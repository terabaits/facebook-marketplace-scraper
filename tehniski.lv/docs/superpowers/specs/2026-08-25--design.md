# tehniski.lv — Design Spec

**Status:** Draft (post-review v2)
**Date:** 2026-08-25
**Owner:** Mavis (planning), qljz7 (implementation)
**Domain:** tehniski.lv (Latvian tech news portal)

---

## 1. Context

A Latvian-language tech news portal at `tehniski.lv`. Two halves of the system:

1. **Editorial pipeline** (we own and run): a scheduled worker fetches RSS feeds from 6 English-language tech sources, scrapes each article, and stores the markdown. An admin-triggered AI workflow picks the day's top stories, has a human approve, then writes Latvian articles. Drafts can be reviewed and published from the admin panel.
2. **Public website** + **admin panel**: the website displays published Latvian articles with threaded comments and ads. The admin panel manages posts, comments, ads, RSS sources, scraped story stash, the newsletter HIL workflow, and LLM prompt templates.

The original n8n-based design was set aside — we build the pipeline ourselves inside the same Next.js codebase.

### Brief inputs (from the user)

- 6 RSS sources: Digital Trends, Tom's Hardware, Windows Central, Ars Technica, CBS News SciTech, Technobuffalo
- Public site = tech/programming vibe, dark + light mode
- Homepage: 2 big thumbs, 4 medium thumbs, 3-col grid for older posts, ad banners on the right rail
- Post detail: top ad banner, right-rail ad, intro + body, comments
- Comments: nick + email, threaded
- Admin can post comments with an "Author" badge
- Admin panel: posts, comments, ads, prompt templates, scheduling
- Skip Firecrawl — we build our own scraper (user has `/web-scraper` skill)
- All UI in Latvian; AI translates English sources → Latvian output
- Future: consider OpenTilde (or similar dedicated translation API) if LLM-translated Latvian quality is poor

## 2. Decisions summary

| Decision | Choice |
|---|---|
| Content model | Each "core" newsletter story → 1 website `Post`. Daily digest is not modeled separately. Newsletter intro/shortlist are not stored as separate public artifacts. |
| Stack | Next.js 16 (App Router) + TypeScript + PostgreSQL + Prisma + Tailwind v4 |
| UI components | shadcn/ui (Radix + Tailwind, copy-paste, owned source) |
| Ads | Hybrid: self-managed creatives (image + URL) primary; raw HTML/JS embed slot for AdSense-like fallbacks. One impression per ad unit per page view (client-side, on mount). |
| Comments | Threaded (arbitrary depth), post-moderation, denormalized `reply_count` + `last_reply_at`. Top-level and replies both sort oldest-first. |
| Homepage ranking | Hybrid: manual `featured_tier` (big/medium) override + fallback to recency |
| Author comments | Admin posts comments via `POST /api/admin/comments` with `is_author=true`. Top-level when `parent_id` is null; reply when `parent_id` is set. |
| Scrape library | `cheerio` + native `fetch` (Node 18+) + `@mozilla/readability` primary, `playwright` fallback per source |
| Worker scheduler | `node-cron` in a separate `next-worker` process, supervised as a Windows Service via `nssm` |
| Editorial AI | **Mavis-driven manual workflow for v1.** The HIL UI in admin lets the admin prepare a "task packet" (formatted prompt + scraped stories) and copy it into chat with Mavis. Mavis returns structured JSON. Admin pastes the JSON back; the system parses and saves. No external LLM API in v1. **Architecture is LLM-ready:** when the user later switches to an API call, only `lib/editorial/executor.ts` changes — the JSON schema and storage stay the same. |
| Translation | Mavis (the AI) does inline translation + writing in one pass. Future: swap to a dedicated translation API (e.g., OpenTilde) if Latvian quality is poor. |
| Deployment | Self-hosted Node (`next start` on port 5002) on the existing Windows machine, both processes as `nssm` Windows Services. Cloudflare Tunnel in front for `tehniski.lv` HTTPS. |
| Search | Postgres FTS (Latvian config) with GIN index on `tsvector` generated column |
| Auth | Auth.js with email magic link, delivered via Resend |
| Email provider | Resend (transactional, free tier covers v1 volume) |
| Image storage | Local `./uploads/` for dev; S3-compatible (Backblaze B2) for prod. Uploads via signed PUT URL. |
| Language | Latvian only for v1; UI strings in `lib/lv.ts` |
| Slug policy | Keep Latvian diacritics. Pre-normalize (NFC + diacritic-fold) for collision check only. |
| Time zone | DB stores `TIMESTAMPTZ` in UTC. All user-facing time formatted in `Europe/Riga`. |
| DB collation | ICU collation `latvian` (provider=icu, locale='lv') for any column with Latvian text sort. |
| Error tracking | GlitchTip or any Sentry-compatible service from Phase 0 (start with a hosted free tier; self-host only if user explicitly requests it later) |
| Comment email | Hashed (sha256) before storage. Plaintext not retained. |
| Tags | **Out of scope for v1** (data model dropped). Reintroduce in v1.1 if needed. |
| Analytics | **Basic v1:** post view count (`Post.view_count` + 1 per public page view, deduped by `ip_hash` per 30 min), aggregated stats in `/admin/analytics` (top posts, ad performance summary, comment volume, search queries). No third-party analytics (Plausible / Umami) in v1 — too much surface area. Self-hostable later. |
| Multi-author | **Out of scope for v1**. `Author` table exists for forward-compat; admin uses single seeded Author. No `/admin/users` page. |

## 3. Architecture & data flow

### Topology

Single Next.js 16 repo. Two runtime processes, both supervised as Windows Services:

- **`next start`** (web server, port 5002) — public site + admin panel + API routes
- **`next-worker`** (background process) — node-cron scheduler + RSS fetcher + scraper + scheduled-publish job

Both connect to the same Postgres. Web and worker are independent — a stuck scrape never blocks the web server.

### Trigger table

| What | Trigger | Where |
|---|---|---|
| RSS fetch + scrape | Cron every 3h | Worker |
| Newsletter "pick top stories" | Admin clicks `Sagatavot uzdevumu` (prepare task), copies packet to chat with Mavis, pastes Mavis's JSON back | API route (admin) — receives pasted JSON, validates, saves |
| Newsletter "rewrite per feedback" | Admin types feedback, regenerates packet, re-pastes Mavis's new JSON | API route (admin) — receives new JSON, replaces prior candidates |
| Newsletter "write core sections" | Admin clicks `Sagatavot uzdevumu` per approved story, pastes Mavis's markdown response | API route (admin) — receives markdown, saves as draft post |
| Newsletter "publish" / "schedule" | Admin clicks publish | API route → flip status |
| Scheduled publish | Cron every 1m | Worker — flip `status='scheduled'` rows where `publish_at <= now()` |
| Public comment | Form post | API route |
| Admin top-level "Author" comment | Admin uses admin-side comment form | `POST /api/admin/comments { post_id, body, is_author: true }` |
| Admin "Author" reply | Admin clicks "Reply as author" | `POST /api/admin/comments { post_id, parent_id, body, is_author: true }` |
| Comment moderation | Admin clicks approve/spam/delete | API route |
| Ad impression/click | Browser hits `/api/ads/track` | API route (impression fires once per ad unit per page view, client-side) |

### Editorial AI (Mavis-driven, v1)

For v1, the editorial AI is **Mavis** (this agent), accessed via chat. The admin is the bridge: they prepare a "task packet" in the admin UI, copy it into chat with Mavis, and paste Mavis's response back into the UI for parsing and storage.

**Why this design**

- The user explicitly chose to do AI work out-of-band (Mavis in chat) instead of integrating an LLM API. Reasons include: no API costs, full control over editorial quality, no vendor lock-in for v1, easy to switch to a paid LLM later.
- The architecture is **LLM-ready**: when the user wants to switch, only `lib/editorial/executor.ts` changes. The packet-builder, JSON schema, and storage are reusable. The HIL UI is the same.

**Workflow per HIL step** (e.g., "Pick top stories")

1. Admin opens `/admin/newsletter/[id]` and clicks **Sagatavot uzdevumu** ("Prepare task") for the current step
2. UI shows a modal with:
   - **Task packet** (markdown, ready to copy): includes the system prompt, the scraped stories (title, source, summary, body excerpt), the previous newsletter text (if dedup), the editorial feedback from the previous iteration (if any), and the strict JSON output schema Mavis must return
   - **Response paste area** below
3. Admin clicks "Copy task to clipboard" → switches to Mavis chat → pastes → Mavis returns JSON
4. Admin pastes Mavis's JSON into the response area → clicks "Submit"
5. UI parses the JSON, validates against the schema, shows a preview, and on confirm saves to DB and advances the workflow

**JSON schemas (defined in `lib/editorial/schemas.ts`)**

Each HIL step has a strict schema. Example for `pick-stories`:

```ts
{
  candidates: [
    {
      story_id: string,        // ScrapedStory.id
      title: string,
      source: string,          // RssSource.name
      reasoning: string,       // 1-2 sentences
      rank: number             // 1 = top pick
    }
  ],
  intro?: string,             // ~1 paragraph Latvian intro for the day; auto-fills first post's excerpt
  shortlist?: string[],       // titles of runner-up stories not picked; logged in NewsletterRun
  iteration_notes?: string    // what changed vs prior iteration
}
```

Other step schemas: `subject-line` (main + 3-5 alternatives), `core-section` (markdown body + title + excerpt per approved story). The `intro` paragraph and `shortlist` of runner-up stories are folded into the `pick-stories` response (optional `intro?: string` and `shortlist?: string[]` fields on the candidates JSON) — keeps the HIL editor tab to a single round-trip per iteration. All are Zod-validated before save.

**Packet builder (`lib/editorial/packet-builder.ts`)**

Generates a self-contained task packet. Each step has its own builder that:
- Pulls the right DB context (scraped stories for the run, prior picks, etc.)
- Includes the user-editable system prompt (editable in `/admin/prompts`, stored in `PromptTemplate`)
- Includes the JSON output schema inline
- Caps markdown body excerpts at 10KB per story to keep packets manageable for paste-into-chat
- Wraps scraped content in `<source>...</source>` delimiters and tells Mavis to treat it as data, not instructions (defense in depth even though Mavis is trusted)

**Future: API integration**

`lib/editorial/executor.ts` exposes a single function: `runStep(step, packet): Promise<ResultJson>`. In v1, this function returns a placeholder that triggers a UI "paste response" flow. When the user later wants an LLM API, this function calls `claude-sonnet-4-5` (or whichever) with the same packet; the rest of the system is unchanged.

**Risk mitigations that change with this design**

- **No LLM cost risk** for v1 (zero API spend). Risk becomes: Mavis availability and response quality. Mitigated by: admin can iterate freely (paste new response), no automatic publishing.
- **No prompt injection from scraped content** in the v1 sense (Mavis is trusted). But the `<source>` delimiter convention is still used in packets as a defensive habit.
- **Daily LLM cap** is dropped from v1. Reintroduce when API integration is added.

### Auth.js ↔ Author mapping

- Auth.js manages its own user/session tables
- The `Author` table is the editorial record (for `Post.author_id`, `Comment.author_id`)
- Mapping: `Author.email == session.user.email` (case-insensitive). No `auth_user_id` column.
- First-admin bootstrap: `npm run seed -- --email=you@example.com` creates one `Author` row
- On any admin request: middleware looks up `Author` by session email. If missing and email matches a seeded admin email, auto-creates the `Author` row on first login. If missing and not admin email, deny.

### Worker process

A single file (`worker/index.ts`) that:

1. Connects to the same Postgres + reads `RssSource` rows
2. Schedules a cron job (`0 */3 * * *`) that, per source:
   - Fetches the RSS feed (XML parser)
   - Filters URLs already in `scraped_stories` by `url_hash`
   - For each new URL: scrapes via `cheerio` + `@mozilla/readability` (or `playwright` if `parser_config.kind === 'playwright'`)
   - Stores result as `scraped_stories` row with `status='new'`
   - Updates `RssSource.last_fetched_at` and clears `last_error` on success
3. Schedules a second cron job (`* * * * *`) that publishes scheduled posts
4. Logs to stdout; failure modes write to `RssSource.last_error` and trigger a GlitchTip event
5. Exposes a health-check heartbeat: writes `worker_heartbeat` row every 60s (separate small table for liveness checks)

Launched by `npm run worker`. Supervised via `nssm` with `AppExit Default Restart`.

## 4. Data model (Prisma)

All tables in one schema. Conventions:

- IDs: `cuid()`
- Timestamps: `created_at`, `updated_at` everywhere; all time stored as UTC `TIMESTAMPTZ`
- Soft delete via `deleted_at` on user-facing content (`Post`)
- Indexes on every foreign key + on common query shapes
- One raw SQL migration owns the `tsvector` column (no Prisma type, no nullable flag)

### Public site

```prisma
model Post {
  id              String   @id @default(cuid())
  slug            String   @unique
  title           String
  excerpt         String   @db.Text
  content_md      String   @db.Text
  // content_html is generated from content_md on every save (Post create/update API
  // route runs the markdown through `lib/markdown.ts` → sanitized HTML and writes both).
  // This keeps Server Components cheap (no per-request render) and lets us cache the
  // HTML version when the post is published.
  content_html    String   @db.Text
  cover_image_url String?
  cover_image_alt String?
  status          PostStatus
  publish_at      DateTime?            // TIMESTAMPTZ
  published_at    DateTime?            // TIMESTAMPTZ
  language        String   @default("lv")

  // 1:1 link to the scraped source story (newsletter-generated posts only).
  // No Prisma relation declared; query via findUnique({ where: { source_scraped_id } }).
  // Enforced unique at the DB level (raw migration adds UNIQUE constraint).
  source_scraped_id  String?       @unique
  source_url         String?
  newsletter_run_id  String?       // FK → NewsletterRun
```

### Migrations

Prisma migrations directory. Four raw SQL migrations added on top:

- `0002_post_search_vector.sql` — add generated `tsvector` column on `posts(title || excerpt || content_md)` with GIN index, config `'latvian'`. The column is **not** in the Prisma schema; Prisma simply ignores it.
- `0003_scheduled_publish_index.sql` — partial index `CREATE INDEX post_scheduled_publish_idx ON posts (publish_at) WHERE status = 'scheduled'`
- `0004_icu_collation.sql` — `CREATE COLLATION IF NOT EXISTS latvian (provider = icu, locale = 'lv', deterministic = false)`. Applied via `COLLATE "latvian"` on these sort sites (raw SQL also creates an `ORDER BY ... USING COLLATE` index where useful): `Category.name ORDER BY` (admin category list), `Post.title ORDER BY` (admin post search), `Author.name ORDER BY` (admin user list — even if page is v1.1, index is cheap). All other sorting uses `created_at`/`published_at` which are unaffected by collation.
- `0005_active_prompt_uniqueness.sql` — partial unique index `CREATE UNIQUE INDEX prompt_active_unique ON prompt_templates (key) WHERE active = true;`. Application layer also enforces "only one active per key" on the `activate` endpoint, but this DB-level constraint prevents direct-write races.

### Slug generation

In `lib/slug.ts`:

1. Input: post title
2. NFC-normalize
3. Diacritic-fold ONLY for collision check (`Rīgas` → `Rigas`) against existing slugs
4. Replace whitespace with `-`, strip non-word chars except Latvian letters
5. Lowercase
6. Truncate to 80 chars
7. If collision, append `-{6char nanoid}`

So the actual slug keeps diacritics: `/post/rigas-satiksme-iepirkumus`. Collision check works against both the diacritic-stripped version and the original.

### Comment denormalization rules

- `depth` set on insert: `parent.depth + 1` (or 0 for top-level)
- On insert with `parent_id`: `UPDATE Comment SET reply_count = reply_count + 1, last_reply_at = COALESCE(last_reply_at, NOW()) WHERE id = $parent_id`
- On delete: `UPDATE Comment SET reply_count = reply_count - 1 WHERE id = $parent_id` (no `last_reply_at` change)
- Race conditions: rare on a news site, mild staleness is acceptable

### Date / time formatting

`lib/format.ts` exports:

- `formatDateLv(d: Date): string` → `"25.08.2026."` (Latvian: `dd.mm.yyyy.`)
- `formatDateTimeLv(d: Date): string` → `"25.08.2026. 14:35"`
- `formatNumberLv(n: number): string` → comma decimal, space thousands (`"1 234,56"`)
- All functions take a UTC `Date` and render in `Europe/Riga` timezone
- `formatRelativeLv(d: Date, now: Date): string` → `"pirms 2 stundām"`, `"vakar"`, `"šodien"`

### Comment sort order

- Top-level comments on an article: **oldest first** (preserves conversation flow)
- Replies within a thread: **oldest first** (chronological conversation)
- UI toggle per page: "Jaunākie" / "Vecākie" (newest / oldest)
- Default: oldest first

### HIL workflow page (`/admin/newsletter/[id]`)

Four tabs, state-machine style. Per-step UX:

1. **Editor** — "Sagatavot uzdevumu" button opens modal with the task packet (markdown, copyable). Admin copies, pastes into chat with Mavis, pastes Mavis's JSON response into the modal's response area. UI validates JSON against schema, shows candidate cards (Approve / Skip / Move), feedback textarea, "Atkārtoti sagatavot uzdevumu ar atsauksmēm" (re-prepare with feedback) for iteration
2. **Subject** — same pattern: packet → Mavis → JSON response (main + 3-5 alternatives) → "Izmantot šo" picks the chosen one
3. **Write** — per-approved-story: packet → Mavis → markdown response → preview in markdown editor → Save as draft / Re-prepare task / Publish now
4. **Publish** — final review of all drafts (intro auto-fills first post's excerpt, shortlist logged in `NewsletterRun`), bulk Publish / Schedule

**The "Prepare task" modal is the key UX element:** every step uses the same flow. Each packet is self-contained (system prompt + relevant DB context + JSON output schema), so the admin can run any step independently without back-and-forth setup.

**Newsletter intro + shortlist (revised scope):** The AI workflow generates the intro paragraph and a shortlist of runner-up stories as part of the editor step. These are **not** published as separate posts. Instead, on Publish, the intro is automatically set as the first post's `excerpt` (if not already set), and the shortlist is logged in the `NewsletterRun` record for the editor's reference. This keeps the public data model clean: one newsletter run = N published posts, each with their own page.

## 8. Risks

| Risk | Mitigation |
|---|---|
| Latvian LLM quality is poor | Test in Phase 6 with real scraped content before Phase 7 builds the UI on top; swap models, tune prompts, or add a dedicated translation API if needed |
| Some RSS sources are JS-heavy and don't scrape cleanly | Per-source parser config + playwright fallback + "failed" status so the bad ones don't block the rest |
| Self-hosting Next.js 16 on Windows is less common than Linux | Use the Node production server (`next start`), document `start-all.ps1` for local dev; production uses `nssm` services (Phase 4b) |
| Worker dies → no scraping for 3h | `nssm` with auto-restart (Phase 4b) + admin dashboard "worker last seen" badge with red alert if > 6h + GlitchTip event on repeated failures |
| Comment spam at launch | Rate limit (5/min/IP), post-moderation, one-click spam button in admin. **Multi-process deploy caveat documented** (in-memory bucket per process). |
| Latvian diacritics break in URLs/search | Slug policy keeps diacritics; FTS uses `'latvian'` config + `lv_LV` ICU collation; UI strings handled via `lib/lv.ts`; date/number formatting via `lib/format.ts` |
| **Transactional email provider missing** (no email = admin can't log in) | Resend account + sender domain verification is a **Phase 0 deliverable** before Auth.js can be tested |
| **Image/object storage not decided** (covers, ad creatives) | Phase 0: local `./uploads/` for dev. Phase 4b: Backblaze B2 (S3-compatible) for prod, via signed PUT URLs from admin |
| **No backup / disaster recovery** | Phase 4b: `pg_dump` cron to local disk + daily copy to Backblaze B2; documented restore procedure |
| **LLM cost overrun** | **N/A for v1** — no LLM API in v1 (Mavis is manual). Reintroduce if/when LLM API is added. |
| **Mavis availability for editorial workflow** | Admin can pause a `NewsletterRun` and resume later; packets are persisted so the workflow survives Mavis being offline; admin can iterate on the JSON response as many times as needed; "I can't help right now" handled by waiting until Mavis is available. |
| **Prompt injection from scraped content** | All scraped markdown wrapped in `<source>...</source>` delimiters; packet text tells Mavis to treat inside as data, not instructions; markdown body excerpts capped at 10KB per story. Lower risk in v1 since Mavis is trusted, but defensive habit kept. |
| **Source-site IP bans** (self-hosted on home IP) | `last_error` field; GlitchTip event on consecutive failures; admin dashboard red badge; respect `robots.txt`; per-source rate limit config in `parser_config` |
| **GDPR** (EU site) | `Comment.author_email` hashed (sha256) before storage; plaintext never retained. `/privacy` page documents retention. `AdEvent.ip_hash` already hashed. |
| **Auth.js ↔ Author mapping ambiguity** | Documented: `Author.email == session.user.email`; auto-create `Author` row on first admin login if email matches seed |
| **Multi-process rate-limit weakening** | In-memory bucket per process; documented swap-to-Redis path; single-process is v1's target |
| **Comment retention / GDPR right-to-be-forgotten** | `status='deleted'` soft delete (keeps thread shape); admin can hard-delete via `DELETE /api/admin/comments/[id]` (GDPR workflow). |
| **Cover image copyright** (scraped images republished) | LLM prompt for cover image picks: prefer "no image, use generated topic SVG", else reference scraped source via `Post.source_url` so the admin can pick a free alternative. Admin always reviews drafts before publish. |
| **News version assumptions** (Next.js 16) | Phase 0 kicks off with explicit version verification checklist |

## 9. Out of scope for v1

- Multi-author support (schema supports it, UI is single-author only; no `/admin/users`)
- Email newsletter sending (this site shows posts; email is a separate system)
- Search via Meilisearch/Typesense (Postgres FTS is enough for v1; revisit when FTS feels slow)
- Dedicated translation API (LLM does it inline; revisit if Latvian quality is poor)
- Image CDN beyond `next/image` (Backblaze B2 in prod, local in dev; no global CDN)
- Comment upvotes/downvotes
- Tags (entire `Tag` and `PostTag` tables dropped for v1)
- Real-time updates (websockets)
- Mobile app / PWA
- Analytics beyond ad impression/click counts
- Newsletter intro/shortlist as separate public artifacts (consolidated into posts)
- GlitchTip/Sentry setup is **in scope from Phase 0** per the §2 decisions table. Use a hosted Sentry-compatible service (GlitchTip cloud free tier, Sentry free tier, or similar) for v1; self-host only if user explicitly requests it later.
